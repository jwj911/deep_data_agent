# 项目全面复审与现代化迭代规格

## 为什么

项目已完成多轮安全与运行治理，但最近的代码提交和规划停留在 2026-08-21。
需要以当前实现、业务目标和官方技术资料判断哪些部分值得更新，形成能推动数据
探索能力的原子化迭代，避免只追逐版本或继续堆积治理工作。

## 变更内容

- 对当前整个项目开展复审，分别评估工程正确性、业务能力与现代化机会。
- 重新核验历史审计的开放项、已关闭项和规划依赖，不直接沿用历史风险等级。
- 核对依赖声明、锁定结果、实际安装版本、运行时支持期及相关安全公告。
- 重点评估真实数据分析闭环、Agent 默认能力、结果溯源、效果评测与前端行为回归。
- 更新既有项目分析与 Roadmap，给出近期优先项、最小实施范围和可验证的收益。
- 同步变更记录；项目指南中的事实发生变化时，再定向更新 README 和 AGENTS。
- 本轮交付是审查结论与迭代建议；发现的代码修复、依赖升级和新功能分别进入后续规格。
- 无运行时破坏性变更。

## 新增要求

### 要求：当前、可复现的审查基线

审查必须记录执行日期、完整 HEAD、工作区状态、规格完成度、环境版本、命令结果
及来源日期。代码基线与实际安装环境必须区分；工作区发生变化时记录新增差异。
历史测试数字、Hosted CI 和容器健康状态不能替代本轮目标源码的证据。

#### 场景：开始正式复审

- **当** 本规格获批并开始实施
- **则** 重新确认基线，检查所需环境，运行适用的现有门禁并记录实际结果。

#### 场景：检查无法执行

- **当** 受支持环境、网络、Docker 或 Hosted 查询不可用
- **则** 记录命令、原因、受影响结论及替代证据，保留“未验证”状态。

### 要求：全项目覆盖与双维度审查

审查必须覆盖真实调用链、模块接口、前后端状态来源、认证与权限、文件生命周期、
数据一致性与恢复、缓存、资源预算、错误与取消、日志、构建部署、依赖、测试和
遗留模块。每个维度须给出检查对象、证据及结论，包括没有发现有效问题的维度。

工程维度检查规范和实现正确性；产品维度检查用户能否完成数据探索任务，以及
新增复杂度是否带来收益。两者分别呈现，不能用规范通过替代业务正确性。

#### 场景：某个模块看起来复杂或过时

- **当** 发现重复封装、职责混杂、旧 API 或未接入代码
- **则** 读取上下文和调用点，以实际维护成本、行为风险或用户影响判断是否值得改动。

### 要求：有依据的技术更新判断

每个更新建议必须提供当前版本或能力、官方支持和变更证据、项目受影响的路径、
最小可行方案、兼容风险与验收门槛。依赖声明、锁文件和已安装版本分别记录。
安全公告必须核对适用版本及实际部署模式，不把静态导出前端等同于 Next.js 服务端。

资料优先采用官方政策、发布记录、迁移指南及原始研究。综合趋势结论尽量由三个
独立来源交叉验证；单源事实、资料冲突或缺口必须明确标注。不得虚构“最新版”、
性能改善、成本收益或行业共识。

#### 场景：评估运行时升级

- **当** 某依赖失去支持或存在与本项目有关的修复
- **则** 区分必要补丁、稳定版迁移和可选功能更新，列出 Auth、thread/run、
  SDK 流式事件、预算 middleware、图包装及容器回归要求。

#### 场景：框架具备项目尚未使用的功能

- **当** 官方新增 Skills、MCP、记忆、规划、子 Agent 或沙箱等能力
- **则** 根据业务需求与隔离成本决定采用、试验或暂缓，不因存在该能力就要求引入。

### 要求：真实数据分析能力评估

审查必须沿“输入文件 → 数据结构与质量 → 确定性计算 → 结果与图表 →
可追溯报告 → 用户取得产物”检查现状。文本预览、聊天回答、图表组件或独立演示页
不能直接计为完整分析能力。

首轮业务建议应优先考虑现有 CSV/JSON 的受控分析工具，比较其与隔离执行环境的
收益和成本。需要执行代码时，另列租户隔离、网络/文件权限、CPU/内存/时间预算、
凭据隔离和产物回收前置；本轮不恢复任意 Python 或宿主机 shell 执行。

#### 场景：用户要求汇总数据并生成报告

- **当** 当前实现只能返回截断文本，或图表数据来源不可验证
- **则** 指出缺失环节，提出包含数据来源、指标口径、计算验证和产物归属的最小迭代。

### 要求：评测支持原子化迭代

审查必须分别评估工程回归和 Agent 效果证据，检查工具选择、结果数值、证据引用、
结构化输出、长上下文、预算、错误恢复及取消。后续评测建议应包含固定的非敏感
任务集、成功标准、失败分类、模型/提示/工具版本记录，以及可获得的延迟和消耗指标。

没有真实模型结果时，只能交付评测方案和现有证据缺口；不得把离线替身或 pytest
通过率描述为真实任务成功率。本轮不增加评测代码或自动发起付费模型调用。

#### 场景：比较升级前后的 Agent

- **当** 建议调整框架、模型、提示、工具或上下文策略
- **则** 给出在同一任务集上对比正确性、失败、延迟与消耗的办法，说明尚未测量的指标。

### 要求：可复核的问题与机会清单

历史问题保留 `AUD-*` 身份，并更新为仍开放、已解决、复发或证据不足。
新条目使用唯一 `REV-*` ID，分别归类为确定缺陷、技术债、业务机会或开放决策。
每项须包含最小代码/文档证据、影响、建议、依赖和可验证的完成条件。

确定缺陷沿用历史 P0–P3 定义：P0 为可直接造成泄露、越权、不可恢复损失或发布
阻断；P1 为高概率重大边界失效、不一致或不可用；P2 为有受控绕行的维护、恢复、
扩展或业务限制；P3 为低风险改善。产品机会另列用户价值、复杂度和前置条件。

两个独立验证者必须分别复核全部候选条目并寻找反证。2/2 支持标为高置信度；
1/2 保留分歧和待确认条件；0/2 从确定结论中排除，必要时作为开放问题记录。

#### 场景：历史文档仍有高优先级问题

- **当** 历史问题与当前源码或目标部署不一致
- **则** 根据本轮证据调整状态与影响，保留历史关联，不照抄原有发布判断。

### 要求：收益与风险共同决定迭代顺序

Roadmap 必须解释保留、更新、合并或暂缓每个既有候选的理由，并区分生产放行
条件、开发中的业务能力前置和可选平台建设。真实隔离、数据恢复和资源边界继续
作为相应能力的前置；完整账号产品化或平台化建设不自动成为所有分析功能的硬依赖。

每个建议迭代必须具有一个主要目标、最小范围、依赖、验收和停止条件。应指出
最值得先做的少量迭代及可并行部分，不预设候选数量，不把全量重写作为默认方案。
收益未量化时使用有依据的定性判断，不伪造工期或性能数字。

#### 场景：恢复风险与运行时升级均需处理

- **当** 两者没有真实实施依赖
- **则** 分别说明风险、业务解锁作用和可并行范围，不仅沿用历史排列。

`project_analysis.md` 必须更新为本轮代码基线的审查快照，保留可追溯的历史

- **则** 文档能够回答“是否落后、落后在哪里、哪些已有设计应保留、先迭代什么”。

### 要求：规划与治理记录一致

`roadmap.md` 必须保留完成里程碑，更新后续顺序、依赖图及问题映射。
`CHANGELOG.md` 记录本轮结论与实际验证边界；README、AGENTS 只修正已失真的
事实。规格、项目分析和规划中的状态、ID、日期及证据不得互相矛盾。

#### 场景：存在未验证的运行检查

- **当** 文档准备交付
- **则** 区分审查文档完成与运行/生产验收状态，缺口不被勾选为运行验证通过。
